# Security Best Practices for LethalBingo

## Handling Secrets

### Environment Variables

This project uses environment variables to store sensitive information like passwords and signing keys. The following files contain environment variable definitions:

- `.env`: Committed default values for the environment variables needed by the app (no real secret, `APP_SECRET` is left empty)
- `.env.prod`: Committed, loaded when `APP_ENV=prod`; holds production-only settings and never a secret
- `.env.test`: Committed values for the test environment only
- `.env.local`: Uncommitted file with local overrides and the real secrets (not tracked by Git)
- `.env.$APP_ENV.local`: Uncommitted environment-specific overrides (not tracked by Git)

`.env.local` is also loaded by every Docker Compose service through `env_file`.

### Best Practices

1. **Never commit real secrets to the repository**
   - Committed `.env` files only hold empty values (or `!ChangeMe!` placeholders in the database defaults)
   - Real secrets are only stored in `.env.local` and `.env.$APP_ENV.local`, which are ignored by Git
   - The container entrypoint refuses to start when `APP_SECRET`, `MERCURE_JWT_SECRET` or `DATABASE_URL` is empty, and in production when one of them still contains a `!Change…!` placeholder

2. **Production Secrets**
   - Production secrets live in `.env.local` on the server, never in the committed `.env.prod`
   - Consider using a secrets management service such as Docker secrets if the deployment grows

3. **Secrets to Define**
   - `APP_SECRET`: Used for CSRF protection, signed URLs and other security features
   - `POSTGRES_PASSWORD`: Database password, also used in `DATABASE_URL`
   - `DATABASE_URL`: Database connection string (`postgresql://app:<password>@database:5432/app?serverVersion=16&charset=utf8`)
   - `MERCURE_JWT_SECRET`: Key used by the app to sign Mercure JWTs and by the hub (embedded in Caddy) to check them

### Setting Up Your Local Environment

1. Create a `.env.local` file (ignored by Git)
2. Define `APP_SECRET`, `MERCURE_JWT_SECRET`, `POSTGRES_PASSWORD` and `DATABASE_URL`, for example with values generated by `openssl rand -hex 32`
3. Start the stack with `just up`

### Setting Up Production Environment

1. Create `.env.local` on the server with the secrets listed above; `compose.prod.yaml` loads it into the container and forces `APP_ENV=prod`
2. Check `TRUSTED_PROXIES` (`private_ranges` by default in `.env`): it must match the reverse proxies in front of the app, so that Symfony sees the real client IP (see login throttling below)

### Docker Images

- The local TLS certificates (`certs/`) are excluded by `.dockerignore` and never copied into any image, development included; in development they are bind-mounted
- The image ships a Caddyfile without development directives: the Vite dev server proxy (`frankenphp/vite.caddy`) and the local certificate are only enabled by `compose.override.yaml`

## HTTP Security Headers

- Caddy adds to every response, static files included: `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Cross-Origin-Opener-Policy: same-origin` and a restrictive `Permissions-Policy`; the `Server` and `X-Powered-By` headers are removed
- Symfony sets the `Content-Security-Policy` (`ContentSecurityPolicyListener`): only the app's own origin may serve scripts, styles, images, fonts and connections, with no inline script and no framing. It is set in Symfony rather than Caddy so the profiler toolbar can add its nonces in development
- Never add an inline `<script>` or an external resource: move the code into a Stimulus controller and the file into `assets/`

## Application Security

### Access Control

- Roles follow the hierarchy `ROLE_ADMIN` > `ROLE_REFEREE` > `ROLE_USER` (`config/packages/security.yaml`)
- `/referee` and `/admin` are protected by `access_control`, and every referee controller also carries `#[IsGranted]`
- Live Component actions that change a game (start, stop, timer, squares) carry `#[IsGranted]` on the action itself: the component endpoint is public, so the check must never rely on the page that rendered the component

### CSRF Protection

- The login form and every Symfony form use CSRF tokens (`config/packages/csrf.yaml`)
- Every route that changes data outside a form (deletions, round and season creation, game notes) requires `POST` and checks a dedicated CSRF token
- Logging out is a `POST` form with a CSRF token, so another site cannot log a user out
- On long-lived pages, the `csrf-refresh` Stimulus controller fetches fresh session tokens from `/csrf-tokens` (authenticated users only, `no-store`) every 10 minutes, which keeps the PHP session alive while the page stays open; each ping also reports how long the page has gone without a click or key press, so it cannot keep an unattended tab logged in (see Session Inactivity)
- Never change data on a `GET` route

### Session Inactivity

- A logged-in user is logged out after `app.session_idle_timeout` seconds without activity (`config/services.yaml`, 8 hours by default, long enough for a referee watching a game without touching it). It is an inactivity timeout, not a maximum session age: someone who keeps using the app is never logged out
- When "Se souvenir de moi" is ticked at login, the timeout is `app.remembered_session_idle_timeout` instead (30 days by default), kept in the session as `_remembered`. The box also sets a signed `REMEMBERME` cookie with the same lifetime, which logs the user back in (with the same long timeout) once the session is gone; it is signed with the password hash, so changing the password invalidates it, and logging out, including for inactivity, deletes it
- `SessionIdleTimeoutListener` keeps the time of the last activity in the session (`_last_activity`), set at login and on every request the user makes: page loads, Turbo visits, form submits
- Requests the page sends by itself never count: the `/csrf-tokens` ping, Live Component re-renders (including the ones triggered by Mercure), Turbo prefetches (`Sec-Purpose` / `X-Sec-Purpose: prefetch`) and the timer resync (`/server-time`)
- Clicks, key presses, wheel and touch events in the page (for example the ones that only trigger a Live Component action) are reported by the ping as `idle`, the seconds since the last one; the server keeps `max(last activity, now - idle)`. A client lying about it only keeps its own session open, and the reporting lag (one ping interval at most) is negligible against the timeout
- Once the timeout is exceeded, the next request logs the user out (session invalidated) with a flash message: a page request is redirected to the login page (logging in again always leads to the dashboard), a Live Component request gets an `X-Live-Redirect` to it, and the ping gets a `401` on which `csrf-refresh` shows the login page, so an unattended screen does not keep showing stale content

### Login Throttling

- After 5 failed attempts for the same username and IP, or 10 for the same IP, logins are blocked for 15 minutes
- Behind a reverse proxy, `TRUSTED_PROXIES` must be set: otherwise every visitor shares the proxy IP and a single attacker can block all logins

### Real-Time Updates (Mercure)

- Anonymous subscribers are allowed on purpose: players follow a game without an account, knowing only its 12-character slug
- A Mercure message (`{"event": ..., "serverTime": ...}` on topic `game/{slug}`, published only by `GameService::refreshGameFrame()`) only tells the open pages of a game which part to refresh (bingo card, timer, steps…); it carries no game data itself
- The page then reloads that part through its Live Component: this request is where game content reaches players, including the label of a square that has just been revealed
- The server filters that response (`BingoService::gameSquares()`): until the game is over, players only get the labels of the always-visible squares and of the squares already revealed; referees get every square
- A hidden square's label is therefore never sent to a player, neither through Mercure nor through the Live Components
- Never put game content (square labels, notes, teams) in a Mercure message: anyone who knows the game slug can subscribe anonymously
